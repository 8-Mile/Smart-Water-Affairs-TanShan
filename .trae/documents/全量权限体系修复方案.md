# 全量权限体系修复方案（RBAC 接口级落地 + 超管通配符修正）

## Context

用户发现「超管能看告警中心」并指出这是逻辑错误。全量审计确认两个系统性问题：

1. **后端 177 个接口中 160 个没有 `require_perm`**，只验 JWT。操作员绕过前端即可删设备、派工单、查用户——前端守卫只是隐藏入口，后端未设防。
2. **超管通配符短路使权限矩阵失效**：`deps.py:85-86` 对 super_admin 直接返回 `{"*"}`、`require_perm:127-128` 对超管直接放行、前端 `permissions.ts:35` 对 isSuper 直接 true。但 bootstrap 的设计意图是「超管仅系统管理」，通配短路让超管实际拥有全站权限，与种子授权矩阵矛盾。

**用户已拍板**：① 查询类 GET（列表/详情/options）只要求登录，写操作严格挂按钮权限码；② 超管去掉通配，按实际授权只剩系统管理权限；③ 其余角色边界维持 bootstrap 现有矩阵。

**已有基础设施**（无需新建）：`bootstrap.py` 的 MENU_SEED + BUTTON_SEED（按钮码已齐备）+ 角色授权矩阵 + `_upsert_*` 幂等模式；`deps.py` 的 `require_perm` 机制；前端 `hasPerm` / `v-perm` / 路由 meta.perm；参考实现 `api/inspection.py`。

## 改动一：超管通配符修复（核心）

| 文件 | 改法 |
|---|---|
| `backend/app/core/deps.py` | `collect_user_perms` 删除 super_admin 返回 `{"*"}` 分支，走正常 RBAC 收集；`require_perm` 删除 super_admin 短路和 `*` 通配判断 |
| `backend/app/api/auth.py` | `_collect_user_perms` 删除 super_admin 返回 `["*"]` 分支（登录/me 下发真实码） |
| `frontend/src/utils/permissions.ts` | `hasPerm` 删除 `if (isSuper.value) return true` |
| `frontend/src/router/index.ts` | 守卫中「超管→system-users」重定向**移到 perm 校验之前**（否则超管访问 /dashboard 先被 perm 校验打进 403，重定向成死代码） |
| `backend/app/services/bootstrap.py` | 新增 `_ensure_super_admin_sys_buttons()`：每次启动把全部 `sys:` 前缀 button 节点对 super_admin「只补不删」授权，作为「超管=系统管理」硬不变量 |

连带已核实无需改：`ExceptionShell.vue` 返回首页按 perms 筛选候选（自洽）；`rbac.py /menus/my` 本就按 role_menu 过滤；`http.ts` 403 跳转机制保留。

## 改动二：160 个接口补权限码（写操作）

模式统一：`Depends(require_perm("码"))`；删除函数内 `_require_super_admin`/`_require_manager`/`role_code in (...)` 硬检，由 require_perm 取代；服务层的「本人/班组」数据校验保留作纵深防御。GET 一律仅登录（现状不动）。

按 API 文件分组（全部用 BUTTON_SEED 既有码，★ 为需新增）：

- **alarm.py**：types 增删改 `alarm:type:create/update/delete`；rules 增删改+复制 `alarm:rule:create/update/delete`（复制复用 create）；repair-handle `alarm:dispatch`
- **repair.py**：POST /repairs `repair:create`；dispatch/reject/complete/accept → `repair:dispatch/reject/process/accept`
- **equipment.py**：equipment-types `eq:type:*`；manufacturers `eq:mfr:*`；maintenance-vendors `eq:maintainer:*`；equipment 增删改 `eq:create/update/delete`（删超管硬检后操作员按矩阵获得 create/update——行为变化，已含在种子矩阵内）
- **org.py**：departments/teams/locations/units 四组写接口统一复用 `sys:dept:create/update/delete`（与前端组织设置页口径一致）
- **scada.py**：runtime start/stop `scada:sim:control`；inject `scada:point:inject`；points 增删改 `scada:point:create/update/delete`
- **water_supply.py**：plans 写 `water:plan:create/update/delete`
- **energy.py**：records 写 `energy:record:*`；prices 写 `energy:price:*`
- **archive.py**：categories 写 `archive:category:*`；upload `archive:upload`；PUT 元数据 ★`archive:update`；DELETE `archive:delete`；favorite 仅登录
- **maintenance.py**：plans 写 `maint:plan:*`；dispatch/auto-dispatch ★`maint:plan:dispatch`；POST /records `maint:record:create`；complete/accept `maint:record:complete/accept`；DELETE /records ★`maint:record:delete`
- **inspection.py**：plans dispatch/auto-dispatch `insp:task:create`；claim ★`insp:task:claim`；complete/补录 `insp:record:submit`（plans 增删改已挂码不动）
- **不挂码**：auth、dashboard、notification、audit（已挂 sys:log:list）、ai.py（AI_ENABLED+透传 JWT 落到目标接口受控）、archive_internal（X-Internal-Token）、scada_ingest（X-Gateway-Token）、health、ws

## 改动三：种子幂等（存量库）

1. BUTTON_SEED 追加 4 条新码（archive:update、maint:plan:dispatch、maint:record:delete、insp:task:claim），`_upsert_buttons` 自动补插
2. 新增每次启动 ENSURE（语义同现有 REVOKE 机制，仅针对新码，存量库「缺失=从未授予」，不覆盖管理员手工配置）：
   - 领导 ensure：4 个新码
   - 操作员 ensure：`insp:task:claim` + `repair:create`（操作员认巡检、巡检异常发起工单的刚需；现端点仅登录所以缺口未暴露，挂码前必须先 ensure）

## 实施批次（每批独立可验证）

- **B0** deps.py + auth.py 去通配 + bootstrap 超管 sys 按钮 ensure → 验证 /auth/me 超管仅 sys:* 码
- **B1** 前端 permissions.ts + router 守卫顺序 → 验证超管落地 system-users、直输 /alarm/realtime 进 403
- **B2** 种子：4 新码 + 领导/操作员 ensure → 验证三角色 role_menu 增量正确
- **B3~B6** 按域挂码：org → equipment → repair/alarm/maintenance/inspection → water/energy/archive/scada
- **B7** 清理：失效注释、`'*'` 残留、前端 SimpleCrud 页面 writeRole 模式逐一核对（Teams/Units/Equipment 页必须与后端码一致，防止「按钮亮但 403」或反向）

## 回归验证矩阵（摘要）

| 场景 | 超管 | 领导 | 操作员 |
|---|---|---|---|
| 登录落地页 | system-users | dashboard | dashboard |
| 直输业务页面 URL | 403 页 | 正常 | 正常 |
| curl 写业务接口（派发/删除/上传等） | 403 | 200 | 按码：repair:create/claim/complete 等 200，删设备/上传档案 403 |
| curl POST /system/users 等系统接口 | 200 | 403 | 403 |
| GET 列表/options/stats | 200 | 200 | 200 |
| 无 token | 401 | 401 | 401 |

每批先用 curl 按矩阵过一遍（三角色 token），再做浏览器验收（菜单、按钮显隐、403 页、返回首页链路）。

## 风险与注意

1. equipment 删硬检后操作员真正获得 eq:create/update（种子矩阵本就如此设计，属生效而非越权）
2. GET 坚持一律仅登录——options 下拉被跨页复用，给 GET 挂码会连锁炸页面
3. ENSURE 只含新码+repair:create，不回灌旧码，不覆盖管理员手工配置
4. 挂错码会导致操作员动作被弹 403 页，每批必须 curl 全量验证后再浏览器验收
5. 若有运维脚本用 admin token 调业务写接口（如 auto-dispatch 手动触发），通配移除后会 403，需改用领导账号——部署侧排查
