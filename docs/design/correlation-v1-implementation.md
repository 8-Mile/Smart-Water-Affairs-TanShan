# 唐港智慧水务 · 跨系统异常关联与协同处置 V1

## 一、功能定位

本模块是原有「智能运行 → 集中值守中心」的能力深化，解决多个工艺告警是否有关联、如何避免多头受理和重复派工、怎样形成可核实的事件闭环的问题。

核心原则：**同设备业务事件可以按明确资产ID归集；跨工艺时间接近仅是待核实线索，不作为物理管网关系和共同根因证据。**

### 已核查的本地DEMO素材

- 设备资产：P-001/P-002/P-004（中压供水）、SP-004（射雾器）等，均为MOCK。
- 实际DEMO已有告警：ALM-P002-01（2号泵振动）、ALM-P002-02（2号泵电流，故障演示情景）、ALM-SP004-01（4号射雾器末端压力，故障演示情景）。
- 中压供水既有检查工单：WO-2026-014，关联P-002。
- 原智能值守支持P-002压力异常及数据缺失事件 UT-*，单个异常经两轮演示巡查后生成，业务源仍由原值守模块控制。
- **现有ProcessBinding的verifiedPhysicalLink均为false，无法确认P-002和SP-004真实供水关系；原始示例并不支持自动给出“上游供水导致射雾压力下降”结论。**
- 独立演示模式读取 `buildSeed("SCN-PUMP-FAULT")` 的真实已有MOCK场景，不修改当前全局业务场景、原告警或工单。

## 三、页面

1. **顶部**：当前平台场景 / 独立P-002与射雾器故障演示切换。MOCK预览不改动平台当前数据。
2. **业务状态**：活动生产/值守信号、同设备归集组、跨工艺待核实线索、正在协同处置数量。
3. **左侧关联队列**：按设备资产ID归集活动生产告警和未关闭值守事件，并复用原工单引用。
4. **右侧单事件处理**：原始告警/值守时间戳与状态、工单关联、关联假设、人工受理→协同处理→恢复核验→关闭、审计日志。
5. **底部跨系统线索**：24h窗口内不同行业工艺的两个活跃异常仅构成“时间接近”；录入资料编号和说明、提交人工DEMO审核后，才可作为协同核查的业务假设；仍不得称为真实物理关联。
6. **恢复回放与独立处置记录**：人工受理后的协同记录独立保留，即使活动告警已经全部解除也不从队列消失；人员仍能核验源ID及关闭前的工单状态。
7. **仅MOCK恢复验证**：在独立故障预览并推进至“待恢复核验”后，点击「模拟告警解除与工单验收（仅DEMO）」可切换为只读的恢复样本（源报警状态演示为closed，工单演示为archived）。这个操作不改变任何平台原始告警、工单和设备，只用于验证业务闭环的状态校核；之后仍需人工填写核验说明才能关闭。
8. **信息边界**：始终说明现场拓扑、共用测点、可靠的因果规则仍未知。

## 四、实际执行的确定性业务规则

### 事件输入

- 从现有 `useDemoStore().alarms` 获取活动production告警（包含已确认但未关闭的告警）；budget类business告警不当作生产设备故障。
- 从 `useUnattendedStore().events` 获取活动值守事件；关闭或误报归档的值守事件不参与新归集。
- 活动事件统一保留 `source:id`、assetId、subsystemId、发生/最后更新时间、状态、严重点位和已有关联工单ID。
- 原资产、原告警、原工单作为事实性引用，模型不另造生产告警、替换设备或关闭源事件。

### 同设备归集

- 同一assetId的一组告警/值守事件展示在同一队列内，保留独立原ID。
- 若原报警或当前设备已有在办工单，优先复用其ID，不为同一事件自动产生新工单。
- **这种归集只是共同设备与业务引用，不等于断定多个告警源于同一故障。**

### 跨系统候选

- 将不同subsystemId、不同assetId、事件时间差在24小时内的活动信号匹配为潜在关联线索。
- 每组设备对只保留一条候选，避免同源多个告警导致候选泛滥。
- 如果没有明确审核过的关系登记，则属于 `temporal_only`，**严禁跨工艺自动合并、判定根因或据此创建联合执行命令**。
- 操作员可提交关系索引、解释和审核申请；管理者/管理员复核后只得到 `reviewed_demo`，含义是“演示流程中已审阅人工假设”，**不是现场已验证管道/供水/设备连接**。
- 仅复核后的DEMO关系可以进入同一“协同核查”范围。
- 已有一个协同事件覆盖的另一端设备，也打开同一份记录；不能产生第二个同源协同事件和第二张重复工单。

### 协同处置状态机

`待受理 → 已人工受理 → 协同处理中 → 待恢复核验 → 已闭环`。

- 各阶段需人工填写不少于8字的记录，附时间及角色。
- 原生产告警、值守事件状态**不由协同模块改写**。
- 最终人工关闭必须同时满足：原始相关sourceID均可访问且已关闭、所有已连接设备**没有新的活动异常**、已有设备工单均已验收归档。
- 已受理事件与原始活动告警状态解耦：所有源告警解除后，仍可在协同队列中查看待闭环记录与审计，直至人工确认关闭；关闭后仍保留可追溯记录。
- 若当前的独立MOCK故障源仍在报警，关闭操作会报错并保留事件在“待恢复核验”，这是本期设计的正确结果。
- **“关闭协同事件”不等于实际设备恢复运行**；当前没有实时确认现场测量的能力。
- DEMO候选关系只允许人工审核与协同核查，不驱动泵、阀、PLC，也不会更改其他工艺系统。

### 工单对接

- 用户有权并且在**当前真实DEMO场景（非只读故障预览）**时，才允许在协同受理后尝试创建一份检查工单草稿。
- 若已有工作中工单，则直接复用原ID并下钻；不会重复派工。
- 没有现有工单时，调用原 `demo.createWorkOrder()`，携带全部关联的原始源ID；创建状态仍为原业务模块的草稿。
- 在预览态禁止创建平台业务工单，避免独立预览的输入与全局真实场景混用。

## 五、权限

- `correlation:link`：duty、manager、admin；提交演示关系依据待审核。
- `correlation:review`：manager、admin；进行DEMO业务关系复核。
- `correlation:handle`：duty、manager、admin；受理与推进协同事件。
- 生成工单另需 `workorder:create` 原有业务权限。
- viewer、engineer、水资源角色只能查看跨系统分析，不得绕过角色授权写记录。

## 七、工程与试点边界

**已实现，可现场DEMO验证**：从现有告警/值守事件/工单动态读取、同设备事件归集、24h时序候选、人工业务关系登记与复核、稳定协同事件ID、防重复受理、工单复用、处置状态与审计、恢复门槛检查。

**尚未实现，不能在汇报中宣称已完成**：
1. 真实管网供水拓扑、阀门/泵站实际连通、已审核的跨工艺因果关系。
2. 跨六套工艺的完整在线SCADA测点覆盖和准确授时。
3. 复杂根因模型（贝叶斯、事件传播图、故障树、动态关联和安全控制策略）。
4. 独立业务后台、正式审计留痕、防篡改服务端数据库、多人并发流程、授权电子签章。
5. 恢复现场验证、工单自动派发、向PLC下发任何控制动作。

**前端工程事项：** 本次生产构建通过，但Vite仍提示主JS chunk 大于500kB。后续全局性能优化时应将工艺、地图、图表与AI工作台的重型模块按路由异步加载，避免仅靠增加功能使首屏资源持续增长；不属于这次跨系统业务模型的验收指标。

正式部署时，先收集业主的P&ID、管网连接图、测点表/质量与时间戳、事件处理规程和工单字段，核实实际连接并形成经过岗位授权的跨系统规则。优先从同设备/同母管的真实事件开始试点，再逐步扩展六套工艺的多源分析。

## 八、下一步

第七个亮点建议「专业知识库 + 有来源的异常解释」：给当前事件和工单关联已审核的设备手册、管网资料、规程和历史维修记录，明确参考版本、适用范围及审计责任。避免AI搜索出无来源结论。
