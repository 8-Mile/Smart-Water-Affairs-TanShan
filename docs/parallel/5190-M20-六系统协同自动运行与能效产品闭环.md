# 唐港 5190 · M20 六系统协同自动运行与能效产品闭环

## 1. 产品判断

用户指出：以前各子系统只展示单独设备和局部工艺、情景数据靠人工手动调节、无法解释节能与效率匹配，属于“为了演示而演示”，不满足实际日常使用的系统要求。

本轮确立的产品结构为：

1. **全港水务协同**：集水、污水处理、补水与储水、供水及用水系统组成完整业务依赖链；生活污水与含矿污水独立管理。
2. **自动运行**：现场数据未接入时由持续更新的Mock数据源驱动，供需、储量、规则判断、上下游影响以及水源经济性统一重复计算。日常打开页面不再要求人工启动演示或输入参数。
3. **经营与能效分析**：用同一水量和相同电价/费用口径比选基准、综合成本优先、节电优先；结果可以显示“省钱但多耗电”，不能混淆节水、节电和节费。
4. **人工干预仅留在必要位置**：复杂情景、手工核查和工况调试折叠为高级入口。保留原设备审查、CAD证据与组态发布能力，但不抢占日常运行页面。

## 2. 六系统设计业务链

依据 `frontend/public/tanggang/cad/l1-v2_3/V2.3_区域水路关系.csv` 及 V2.5 六系统分区映射，产品上表达以下设计关系：

| 上游系统 | 下游系统 | 业务方向 | 证据分级 |
|---|---|---|---|
| 雨水收集 | 含矿污水处理 | 堆场/码头雨污水集水、提升进入处理环节 | 设计关系；南侧路径待核 |
| 含矿污水处理 | 水池供水 | 处理达标清水按水质、阀位和接入约束回补 | 设计关系；具体接口未核 |
| 水池供水 | 中压供水 | 除尘水池向中压泵组提供取水条件 | 设计关系；连接未核 |
| 水池供水 | 射雾器除尘 | 泵房与两座除尘水池及射雾供水设计关联 | 设计关系；支管未核 |
| 中压供水 | 雨水收集 | 洗车冲洗供水使用后，经沉淀排水进入南侧集水 | 间接业务路径，**不是两系统直接接管** |
| 生活污水提升与外送 | 独立管理 | 不与含矿污水处理合并成单池 | 系统隔离约束 |

不同系统间的连线是工程业务依赖，**不是物理CAD源Handle与设备接管确认**。原 M19 候选关联审查与端点证据独立保留。

## 3. 自动Mock数据流

- `autoWaterFeed.ts`：纯函数、确定性Mock数据帧，无随机外部数据源或后台写入。模型输入随业务阶段变化（常态、集中用水、泵异常、强降雨、恢复）。
- `store.ts`：统一Pinia情景数据源启动自动模式；每8秒由全局组件推进一个新Mock数据帧，所有现有供水保障、运行监护、雨水风险及六个工艺节点读取同一组输入。
- 运行数据不是每页独立填写，计算流向为 `自动数据帧 → 统一模型 → 供需/储量/雨污水风险/规则 → 六系统影响/能源成本 → 页面`。
- 仅当前浏览器内存，不持久化为正式遥测、报警、维修单、调度指令或PLC控制。浏览器刷新后从默认自动模式重新开始。
- 人工选择情景会切换为手动分析模式，明确恢复自动模式才继续；避免自动更新覆盖人员有意开展的分析。
- 当前Mock帧按模拟阶段循环，**不能视为真实历史趋势，也不证明模型已有现场预测精度**。
- 节能计算和模拟异常使用真实公式，不预设报表百分比。

## 4. 经营分析模型

所有数值来自可追溯的、明确标成“演示假设”的参数（`waterOperations.ts/DEFAULT_WATER_POLICY`），不是业主报价、泵曲线或现场计量：

- 达标含矿水回用：假设供水上限18 m³/h，费用1.1元/m³，水源处理耗电0.66 kWh/m³。
- 市政中水：假设供水上限26 m³/h，费用1.8元/m³，源水能耗0.24 kWh/m³。
- 市政自来水：假设供水上限240 m³/h，费用3.8元/m³，源水能耗0.11 kWh/m³。
- 基准水源份额：假设达标清水10%、市政中水25%、自来水65%；受各自最大供给约束。
- 基准末端泵单耗0.48 kWh/m³、候选优化泵单耗0.42 kWh/m³；上述差额属于演示假设，**不能凭电流直接推算泵的实际节能效果**。
- 假设电价0.8元/kWh，仅用于本模型比较。

统一公式：

1. 已分配供水量：从 `calculateScenario()` 的同轮优先级分配输出读取。需求缺口单独显示，不计入节水。
2. 水源侧电耗：Σ(各水源供水量 × 各自单位取水/处理电耗)。
3. 末端供水泵耗电：已分配供水量 × 候选泵单耗。
4. 总单耗：(水源侧电耗+末端供水泵耗电)/已分配供水量。
5. 综合成本：Σ(源水费用与处理费)+总电耗×电价。
6. 成本优先：在水质资格和流量上限假设约束下，优先选择**含电费的单位综合成本**较低的水源。
7. 节电优先：相同约束下优先选择单位源水电耗较低的水源。
8. 只有各方案供应同样数量的水，才输出电耗和费用差值；容量不足时显示“不可比”，禁止错误计算优化收益。
9. 高峰供水缺口、未核实水质/管线、泵效率曲线缺失，均明确提示为决策前置风险。

**关键产品事实：** 成本优先可能大量使用处理回用水，从而降低采购费用但增加处理电耗；节电优先可能提高自来水占比并增加费用。需要两个指标分别决策，不允许宣称“回用率提高必然节电”。

## 5. 实际界面与操作

- 入口：`http://localhost:5190/port/water/supply`，水资源管理菜单改为“水务协同与能效”；保留原路由兼容。
- 首屏：统一自动运行状态、四个KPI（供需匹配、模型回用率、同量电耗变化、同量成本变化）、六系统流程交互图。
- 业务交互：点击系统进入具体组态；点击连线查看设计业务关系/未核实边界；五套工艺页面增加明确上/下游入口及总览按钮。生活污水单独标识。
- 第二屏：同一模型的成本优先/节电优先水源配比、小时费用、kWh/h、kWh/m³；自动分析规则逐系统查看。
- 第三屏：自动数据帧最近24点内存趋势、计算公式/假设表与工程限制。
- 原有供水专项分析、终端分配、方案比选保留在默认折叠区，不覆盖主业务视图。
- 专业模拟工况调试和节点人工核查默认折叠，仍保留给工程师，不作为普通用户日常操作前提。

## 6. 工程与交付边界

- 软件产品的自动计算、成本比选、风险联动和跨系统关系为实际运行代码；输入数据当前仍然是 MOCK/SIM。
- 本阶段仍没有真实PLC、流量/液位/电耗/水质监测映射，不能声称真实能源节省、现场调度优化或水力可行。
- 补充真实数据后，应替换 **Mock数据适配器**，而不是重做整个业务模型；但必须重新核对单位、时间窗口、供水质量和泵曲线。
- 人员实际干预需要保留操作审批和工程规则，不能把“自动分析建议”当作“自动远程启停”。

## 7. 验收

- `vue-tsc --noEmit`：检查类型。
- `vitest .../__tests__`：验证跨系统关联、同水量成本/节电约束、正常/异常与雨水场景、自动推进、人工覆盖及恢复。
- Puppeteer浏览器：六个节点/五条业务关系/四个KPI；自动运行无需手动触发，8秒推进新帧；点击工艺与返回、公式展开、移动端不出现全页面横向溢出；后台业务写入次数0。
- 浏览器证据：`docs/parallel/evidence/5190-m20-coordination/`。

## 8. 下一阶段的产品化重点

1. **数据接入替换**：测点适配器统一数据质量、时间戳、取样频率，真实数据/估算/缺测/Mock分层。
2. **能耗模型校准**：按设备泵曲线、频率、扬程与实际电表能耗区分供水效率和处理耗电；补全雨污水处理单位能耗和药剂成本。
3. **运营闭环**：自动产生可核实的风险事件候选、显示影响系统与处置建议；人工复核、审批、执行、恢复校验和结果回写，不能用Mock事件冒充正式告警。
4. **工程关系核验**：继续M19候选CAD源Handle核查，明确两座除尘水池与分区集水真实管网，才能为自动调度建立安全边界。
