## 1. 背景与目标

### 1.1 现状

| 资产 | 说明 |
|------|------|
| 旧业务系统 | Java Spring Boot WAR + Shiro + MyBatis-Plus，Tomcat 部署 |
| 旧前端 | Nginx 静态托管（Vue 构建产物） |
| SCADA 同步 | 独立服务 `scada-data-sync-1.0.0.jar`，OPC-UA → MySQL `scada_tag_data` |
| 业务 PRD | 完整字段、状态机、权限矩阵，可直接指导开发 |

旧系统可用作：**OPC-UA 参数、测点命名、表结构参考、业务边界对照**，不作为新代码基线。

### 1.2 重建目标

1. **业务对齐 PRD**：以 V3.0 菜单与状态机为准，补齐/纠正旧系统缺口（尤其告警规则引擎、告警↔工单闭环）。
2. **技术栈现代化**：Python 后端 + Vue3 前端，便于后续迭代与运维。
3. **SCADA 兼容现场**：沿用旧系统 OPC-UA 连接方式与点位配置模式，平滑对接现有 PLC/SCADA。
4. **可分阶段交付**：先打通「设备 → 告警 → 工单」核心闭环，再扩巡检/维保/统计等。

### 1.3 非目标（本期不做）

- 不迁移/兼容旧 Java 代码与旧 WAR 热替换
- 不迁移旧 MySQL 业务数据（空库初始化）
- 不强制复用旧库表结构（新 schema）
- 不重做完整 3D/大屏组态（若 PRD 未强制）
- 不一次上线全部 11 个一级菜单（见分阶段路线）
- 开发阶段不做一键部署安装包

### 1.4 什么是「M3 闭环」

规划里的 **M1 / M2 / M3** 是交付里程碑（Milestone），不是菜单名。

| 里程碑 | 包含阶段 | 一句话 |
|--------|----------|--------|
| M1 | P0–P1 | 能登录，有设备台账 |
| M2 | +P2 | 仿真 SCADA 数据能进库、能看最新值 |
| **M3** | **+P3–P4** | **运维核心业务能从头跑到尾** |

**M3 闭环** = 产品最核心的一条业务链全部打通，可演示、可验收：

```text
① 建设备，绑定仿真测点（变量 ID）
        ↓
② 配告警规则（例如：测点值 > 阈值）
        ↓
③ 仿真把测点值推高 → 系统自动弹出实时告警
        ↓
④ 值班员「一键处理」签收/指派
        ↓
⑤ 操作员「申请维修」→ 自动生成维修工单
        ↓
⑥ 管理员审批派单 → 维修处理 → 提交验收
        ↓
⑦ 验收通过 → 工单归档，告警状态回写为「已关闭」
```

也就是 PRD 里的：

**设备管理（底座）→ 告警管理（感知）→ 维修工单（处置）→ 状态回写**

做到 M3 后，系统已经能支撑现场最要紧的「出事了怎么处理」；巡检、维保、供水能耗、档案等可以在 M3 之后继续做。

## 2. 架构方案比选

### 方案 A：单体 FastAPI + Vue3（推荐）

```
┌─────────────┐     ┌──────────────────────────────────────┐
│  Vue3 SPA   │────▶│  FastAPI（API + Auth + 业务 + WS）    │
│  Nginx      │     │  + 后台任务（告警引擎 / 定时巡检）      │
└─────────────┘     └──────────────┬───────────────────────┘
                                   │
                    ┌──────────────┼──────────────┐
                    ▼              ▼              ▼
                 MySQL         Redis(可选)    OPC-UA Client
              (业务+时序)       缓存/队列      (asyncua)
```

| 优点 | 缺点 |
|------|------|
| 部署简单，和旧 Nginx+后端 模式接近 | SCADA 写入与业务同进程时需做好隔离 |
| 一人/小团队开发效率最高 | 极高点位频率时需拆分 worker |
| 统一鉴权、统一 API | — |

**适用**：当前泵站规模（点位量级与旧配置相当）→ **推荐**。

### 方案 B：双进程（业务 API + SCADA Worker）

- `api`：FastAPI 业务接口、WebSocket 推送  
- `scada-worker`：独立进程只做 OPC-UA 订阅、写库、触发告警事件  

| 优点 | 缺点 |
|------|------|
| SCADA 崩溃不影响 API | 部署/运维多一个进程 |
| 更接近旧系统「独立 jar」形态 | 开发稍复杂 |

**适用**：现场 OPC 不稳定或需要独立重启同步服务时采用。可从方案 A 演进到 B。

### 方案 C：Django + Celery + Vue3

| 优点 | 缺点 |
|------|------|
| Admin 后台快 | API/异步/WS 不如 FastAPI 自然 |
| 生态成熟 | 运维链路更重 |

**不推荐**作为本项目首选。

### 推荐结论

- **默认采用方案 A**（单体 FastAPI + 进程内 asyncio 任务）。
- SCADA 模块在代码层独立包 `app/scada/`，接口清晰，**随时可拆为方案 B**。
- 部署形态继续：**Nginx（前端 + 反代）+ 后端服务 + MySQL**，与旧环境一致。

## 3. 技术选型

### 3.1 后端（Python）

| 层级 | 选型 | 说明 |
|------|------|------|
| Web 框架 | **FastAPI** | 异步、OpenAPI、类型友好 |
| ORM | **SQLAlchemy 2.x + Alembic** | 迁移可版本化 |
| 校验 | Pydantic v2 | 与 FastAPI 一体 |
| 鉴权 | JWT + 角色权限（RBAC） | 替代 Shiro；对齐超管/管理员/操作员 |
| 实时 | WebSocket（FastAPI） | 实时告警、声光提示 |
| OPC-UA | **asyncua** | 对应旧 Milo/OPC 客户端 |
| 任务调度 | APScheduler 或 asyncio 定时 | 巡检生成、维保到期、电费统计 |
| 导出 | openpyxl | Excel 导出 |
| 配置 | pydantic-settings + `.env` | 敏感信息不入库 |

### 3.2 前端（Vue3）

| 层级 | 选型 | 说明 |
|------|------|------|
| 框架 | Vue 3 + TypeScript + Vite | — |
| UI | **Element Plus**（或 Naive UI） | 运维后台表格/表单效率高 |
| 状态 | Pinia | — |
| 路由 | Vue Router（动态菜单） | 按角色加载菜单 |
| 请求 | Axios | 统一 token / 错误处理 |
| 图表 | ECharts | 工作台/能耗/供水/告警统计 |
| 实时 | 原生 WebSocket 封装 | 告警推送 |

### 3.3 数据与中间件

| 组件 | 选型 | 说明 |
|------|------|------|
| 业务库 | **MySQL 8** | 与旧环境一致，便于现场部署 |
| 缓存（可选） | Redis | 会话、测点最新值缓存、去重窗口 |
| 文件存储 | 本地 `uploads/` | 巡检/维修图片、档案附件（与旧一致） |
| 反向代理 | Nginx | 静态 + `/api` 反代 + WS 升级 |

### 3.4 SCADA 对接（对齐旧系统）

参考旧配置：

| 项 | 旧系统参考值 | 新系统策略 |
|----|--------------|------------|
| 协议 | OPC-UA | 保持 |
| 主业务 OPC | `opc.tcp://172.21.96.1:18399`（闸门等） | 配置化 |
| 同步服务 OPC | `opc.tcp://192.168.2.222:9433` | 配置化，可多 endpoint |
| 安全 | Security None + 匿名 | 默认一致，支持用户名密码 |
| 测点 | `ns=1;i=686` / `ns=1;s=Gate1_Status` 等 | **点位表配置**，不写死代码 |
| 落库表 | `scada_tag_data` | 可保留兼容结构或新设计 + 视图兼容 |
| 缓冲 | Disruptor 批量写 | Python：队列 + 批量 insert（500 条 / 1s） |
| 采样 | publishing 100ms / sampling 500ms | 配置化，现场可调 |

**设计要点**：

1. **测点注册表** `scada_points`：tag_name、node_id、value_type、unit、关联设备可选。  
2. **最新值缓存** `scada_point_latest`：告警引擎与前端实时展示读最新值，不扫全历史。  
3. **历史时序** `scada_tag_data`：批量写入；按月分区或归档策略，避免无限膨胀。  
4. **告警引擎** 订阅「最新值变更」事件，按规则匹配，写 `alarm` 表并 WS 推送。

## 4. 系统逻辑架构

```
                    ┌─────────────────────────────────────┐
                    │              工作台                  │
                    │   KPI / 待办 / 趋势（读聚合数据）     │
                    └─────────────────────────────────────┘
  应急优先               │
  ┌──────────────────────┼──────────────────────────────┐
  │  告警管理  ←── 告警引擎 ←── SCADA 最新值             │
  │     │ 一键处理 / 申请维修 / 忽略 / 验收              │
  │     ▼                                               │
  │  维修工单  ←── 审批 / 处理 / 验收闭环                 │
  └──────────────────────┬──────────────────────────────┘
                         │ 设备 ID / 位置 / 变量 ID
  ┌──────────────────────▼──────────────────────────────┐
  │  设备管理（台账底座）  设备分类 / 厂商 / 关联测点      │
  │  设备巡检 / 设备维护（计划驱动）                      │
  └──────────────────────┬──────────────────────────────┘
                         │
  ┌──────────────────────▼──────────────────────────────┐
  │  调度 / 供水统计 / 耗能分析 / 档案 / 系统管理          │
  └─────────────────────────────────────────────────────┘
```

**核心业务闭环（PRD 强制）**：

```
设备(绑定变量ID) → 规则(测点+阈值) → 实时告警 → 一键处理
       → 申请维修 → 自动生成工单 → 审批派单 → 维修 → 验收
       → 回写告警状态(待验收/已关闭)
```

## 7. 分阶段交付路线

> 原则：**先闭环、后扩展**；每阶段可演示、可验收。

### Phase 0 — 工程骨架（约 3–5 天）

**交付**：

- monorepo 脚手架（backend + frontend）
- MySQL 连接、Alembic、JWT 登录、健康检查
- Nginx 本地/内网部署模板
- OpenAPI 文档、统一响应体 `{ code, message, data }`
- 基础布局：登录页 + 侧栏菜单框架

**验收**：可登录空白壳，调通 `/api/health`。

---

### Phase 1 — 系统底座 + 设备管理（约 1.5–2 周）

**模块**：

- 部门 / 班组 / 位置 / 机组 / 用户 / 角色 / 菜单
- 设备分类、设备列表、生产厂商、维保厂商
- 设备绑定 **关联变量 ID（SCADA 测点）**

**验收**：

- 设备台账 CRUD、唯一编号校验
- 分类被引用不可删
- 资产看板：总数/运行/检修/故障 统计

> 对应 PRD 4.5 + 4.11（系统管理子集）

---

### Phase 2 — SCADA 接入 + 最新值（约 1 周）

**模块**：

- OPC-UA 连接（endpoint / 安全策略 / 匿名或账号，参考旧 yml）
- 测点配置导入/维护
- 订阅写入 `scada_tag_data` + 更新 `scada_point_latest`
- 断线重连、批量写库
- 管理端：测点列表、连接状态、最近值预览

**验收**：

- 连上现场或模拟 OPC，点位值持续更新
- 接口可查设备关联测点当前值

**说明（已确认）**：Phase 2 **默认使用仿真**：内置 Mock 推送或本地 OPC-UA 仿真服务；接口形态与真 OPC 一致，后期只改配置切现场。

---

### Phase 3 — 告警管理 + 引擎（约 2 周）⭐ 核心

**模块**：

- 告警类型字典、告警等级（一/二/三类）
- 告警规则配置（设备、测点、比较符、阈值、抖动抑制、重复推送限制）
- 实时告警列表、一键处理、申请维修、忽略、验收
- 历史告警、统计分析（可先做列表+基础饼图）
- WebSocket 推送 + 前端声光提示

**验收**：

- 模拟测点越限 → 生成告警
- 一类告警可自动生单（或配置开关）
- 状态机：未处理 → 处理中 → 待验收 → 已关闭 / 已忽略
- 去重窗口内不重复轰炸

> 对应 PRD 4.2 + 三大模块文档

---

### Phase 4 — 维修工单闭环（约 1.5–2 周）⭐ 核心

**模块**：

- 告警「申请维修」自动生成工单 `RP-YYYYMMDD-XXX`
- 手动报修
- 工单审批 / 处理 / 验收
- 与告警状态双向回写

**验收**：

- 告警→工单→验收→告警关闭 全流程可走通
- 权限：操作员不能验收；管理员可驳回

> 对应 PRD 4.3

---

### Phase 5 — 工作台（约 3–5 天）

**模块**：

- KPI 卡片：今日供水、运行机组、告警机组、本月工单

- 最新调度 + 维修工单待办列表（穿透跳转）

**验收**：首页可运营，待办数字准确。

> 对应 PRD 4.1

---

### Phase 6 — 设备巡检 + 设备维护（约 2 周）

**验收**：计划可生成任务，执行可上传照片，记录可查。

> 对应 PRD 4.4、4.6

---

### Phase 7 — 调度管理（约 1–1.5 周）

**模块**：

- 调度统计 / 调度审核 / 调度任务

> 对应 PRD 4.7

### Phase 8 — 供水统计 + 耗能分析（约 2 周）

- Excel 导出

**数据来源**：SCADA 聚合 + 手工补录。

> 对应 PRD 4.8、4.9

### Phase 9 — 档案 + 系统完善（约 1 周）

**模块**：

- 档案上传/分类/权限下载

## 10. 接口与前后端约定

### 10.1 API 风格

- 前缀：`/api/v1`
- REST 资源化：`/api/v1/equipment`, `/api/v1/alarms`, `/api/v1/repairs`
- 统一分页：`page`, `page_size`, `total`
- 统一错误码：业务错误用明确 `code`（如 `EQUIPMENT_IN_USE`）

### 10.2 实时通道

- `WS /api/v1/ws/alarms?token=...`
- 消息类型：`alarm.created` / `alarm.updated` / `scada.connection`

### 10.3 与旧 Nginx 对齐

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000/api/;  # FastAPI 默认 8000
    # WebSocket
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
}
location / {
    root html;  # Vue dist
    try_files $uri $uri/ /index.html;
}
```
