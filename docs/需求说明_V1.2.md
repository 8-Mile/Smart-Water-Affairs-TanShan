- **A：**《唐山港智慧水务系统技术方案第二版》：已提出射雾器、中压供水、含矿污水、雨水、生活污水、消防以及设备、告警、工单、移动端等需求；属方案内容，不代表所有设备与接口已落实。

- **C：**当前已上传的综合首页设计图与讨论：现阶段以射雾器除尘、中压供水、含矿污水处理、雨水收集、水池供水、生活污水处理六个入口作为**DEMO产品展示口径**。
- **D：**此前讨论形成的升级提案：生成式UI、AI自然语言增删图表、Agent协同、设备健康、能效分析、微观“四预”、语音、BLE巡检等，属于拟增强功能。

**需明确保留的冲突：**原第二版技术方案包含“消防系统”，当前首页用“水池供水”作为第六系统之一；这不是同一概念。本DEMO仅按展示口径设置六个工艺子菜单，消防标注“专业系统扩展/待确认”，不得擅自合并。生活污水与水池供水暂无充分详细工艺图时，不虚构设备及流程。雨水湖区、地下管道及收集关系按“业务示意”表达，不模拟复杂真实水力路径。

### 0.3 优先级、数据标记及成功标准

| 标记 | 定义 | 说明 |
| --- | --- | --- |
| P0 | 第一阶段必做 | 功能可点击、可计算或写入DEMO数据、可重复演示 |
| P1 | 提升版 | 本期可展示局部真实逻辑，完整算法或条件成熟后深化 |
| P2 | 延伸试点 | 接口、原型或说明，不作为一期验收前置条件 |
| OOS | 不做 | 实际PLC远控、新增传感器、重型3D、现场硬件改造 |
| SIM | 演示模拟 | 由统一模拟引擎产生，不得伪装成现场运行实测 |
| REF | 设计参考 | 来源于设计资料，有设计口径及待核参数 |
| CALC | 程序计算 | 可以解释公式、输入、数据范围与假设 |
| AI | 模型建议 | 必须标明依据、限制、审批条件，不视为事实 |

一期DEMO的五项硬性成功标准：六套系统都能进入各自有区别的业务页面；同一模拟数据在首页/详情/报表口径一致；AI能够生成、修改和保存真实组件布局；至少一条异常→诊断→工单闭环；至少一个轻量“四预”场景的输入变化能真正改变计算结果。

## 1. 产品定位与实施边界

### 1.1 产品定位

**一套面向港区管理、生产运行、设备维护和环保水资源人员的AI辅助型智慧水务运营DEMO。** 六个工艺子菜单是业务基础，生成式UI与智能分析是可见亮点，跨系统关联是专业能力。

不以“把首页塞满数据”为目标：首页只回答“现在怎样、哪里异常、下一步做什么”；深度数据与智能能力进入专题页或AI工作区。

### 1.3 明确不做

不进行现场管路、水池、PLC、传感器改造；不画几百亩湖的真实三维地形、地下管道全路径；不承诺真实泵效率和设备剩余寿命；不让Agent直接调用生产控制指令；不允许AI生成任意JS/Vue代码在生产浏览器中执行；不承诺没有数据支撑的节能率或再生水利用率。

## 3. 角色与权限设计

### 3.1 角色定义

| 角色代码 | 使用对象 | 主要诉求 | 权限定位 |
| --- | --- | --- | --- |
| ROLE-MGR | 港区管理者 | 总体态势、专题分析、风险、绩效 | 全局只读+决策审批（如授权） |
| ROLE-DUTY | 运行值班员 | 看工艺、确认告警、发起工单 | 分管系统读/操作告警 |
| ROLE-ENG | 设备运维人员 | 设备健康、工单、维修记录 | 设备/工单编辑与反馈 |
| ROLE-WATER | 环保及水资源人员 | 三水源、雨水、处理与回用分析 | 水资源分析与方案草拟 |
| ROLE-ADMIN | 平台管理员 | 用户、菜单、数据、工作台、规则 | 系统配置、权限授权、审计查看 |
| ROLE-VIEW | 参观/只读用户 | 浏览已授权看板、报告 | 只读，不提交操作 |
| ROLE-DEMO | 演示主持人 | 场景切换、复位、展示不同角色 | 仅演示模式下场景控制 |

一个用户可被赋予多个角色，最终权限按“所属组织、可访问工艺、功能权限、数据范围、审批能力”计算；仅前端隐藏按钮不构成授权控制。DEMO支持右上角“切换演示角色”，生产版本不允许无认证任意切换。

### 3.3 不同角色的登录后体验

- **管理者**：默认“港区运营”模板：首页关注用水、整体状态、重点事件、推荐分析；突出“一键生成报告”和“查看建议依据”。
- **值班员**：默认“运行值班”模板：首页优先重要告警和分管系统；工艺页面优先实时数据与异常；告警可确认/转工单。
- **运维人员**：默认“设备运维”模板：工单待办、设备健康排名、维修历史；只能处理分配给自己或分管组织的工单。
- **水资源人员**：默认“水资源与环保”模板：用水、雨次、蓄水、处理与回用数据；可创建方案草稿、导出分析报告。
- **只读/参观**：隐藏编辑按钮、批量操作、配置入口；只呈现授权数据和经过审核的看板。
- **管理员**：管理用户、菜单、模块开关、模板、字段和数据质量；可查看审计，不允许以配置方式改变工艺联锁。

### 3.4 统一动作规则

所有数据修改具备“前置权限→参数合法性→二次确认（必要时）→提交→结果反馈→审计日志→相关页面刷新”。个人工作台保存不需要工艺审批；发布公共模板、调整关键告警规则、批量配置需要更高权限。演示数据操作在页面醒目位置标注“模拟”。

## 4. 全局布局与交互设计规范

### 4.1 统一桌面布局（目标以1920×1080为主）

| 区域 | 推荐布局/尺寸 | 内容和交互原则 |
| --- | --- | --- |
| 全局顶栏 | 60–64px高 | 项目名称、全局搜索、AI入口、通知、演示标识、角色/账号 |
| 左侧主导航 | 208–216px宽；收起为60–68px | 7个主菜单，工艺监控下六个子菜单，仅一个展开组 |
| 面包屑与页面操作栏 | 44–56px高 | 当前层级、时间/区域选择、页面操作、个人配置入口 |
| 页面主体 | 自适应剩余宽高，外边距16–20px | 固定网格、统一卡片、适当留白，不以卡片数量衡量功能丰富度 |
| 右侧AI工作区 | 可折叠宽380–440px，或独立全页 | 提问、任务过程、生成结果、依据、应用操作；打开时主区响应缩放 |
| 设备详情 | 右侧抽屉480–560px或独立页 | 概要→监测→趋势→告警→工单，支持跨页定位 |
| 全屏工艺/分析 | 单独全屏模式 | 保留退出、返回、告警和数据模式提示 |

**首页严格执行“四指标 + 中央大场景 + 今日关注 + AI全局入口”，不再加底部三列统计卡。** 管理者需要的图表由页面跳转或动态工作台提供。右侧“今日关注”仅包括最多三条告警、两条任务和一条AI建议；无有效建议时不显示空洞文案。

### 4.2 统一状态与异常表现

- 正常、停机、警告、故障、离线、未知/无数据应有不同文本和图标，不仅依赖颜色。
- 红色仅用于重大告警或失败；橙色用于重要风险；绿色用于已确认的正常状态；蓝/青用于信息和交互。
- 真实数据、模拟数据、设计参考值分别采用标识；指标卡可点击查看公式、来源、时间范围。
- 全局时间筛选支持日/周/月/自定义；页面和AI共享当前选择上下文，但各页面可以显式覆盖。
- 表格标准操作：统一搜索、过滤、列显隐、排序、分页（默认每页20条）、导出、空状态、加载状态和错误重试。
- 模拟操作提交后，事件/工单状态立即同步；页面刷新或重新登录不得丢失已持久化的配置。

### 4.3 响应式规则

| 终端 | 布局策略 | 必须可用的操作 |
| --- | --- | --- |
| ≥1600px桌面/展示屏 | 左导航+四KPI+双列主视图；AI右抽屉 | 完整DEMO链路 |
| 1280–1599px | 侧栏可折叠，中央区域优先；右关注面板减宽 | 工艺下钻、告警、工作台 |
| 1024–1279px | 顶部KPI两行/横向滚动，主场景与关注上下排 | 主要业务可操作，无横向截断 |
| 768–1023px | 收起主导航，表格水平滚动或切卡片 | 查询、审核、报表查看 |
| <768px移动端 | 工艺卡片、列表与AI聊天全屏；复杂预演只读或简版 | 告警、工单、查看AI结果 |

DEMO以Chrome/Edge现代浏览器为主，要求在1920×1080与1366×768检验页面无关键内容裁切；小屏不强行展示中央大场景的全部标签。

| C 分析页 | 筛选器+指标摘要 | 关键图表/比较视图 | 结果解释/建议 | 水资源、健康能效 |
| D 业务列表 | 搜索/筛选/批量操作 | 表格或卡片列表 | 右抽屉详情 | 告警、工单、设备 |
| E AI工作台 | 输入/上下文/页面标题 | 动态画布和生成结果 | AI消息及工具过程（可折叠） | DATA-AI |
| F 情景预演 | 场景、参数输入 | 结果图/库容变化 | 风险解释和方案对比 | DEC-FOUR |
| G 配置后台 | 范围与模板选择 | 左树/中央设置/右预览 | 审批/版本/日志 | SYS-* |

### 4.5 六套工艺共用页面外壳（B型）

1. 顶部：面包屑“工艺监控 / 某系统”，右侧放实时/模拟标记、时间选择、收藏和全屏。
2. 第一行：系统名称、运行状态、2–4个**该工艺特有**的关键指标（不能全系统都用相同KPI）。
3. 内部Tab固定：**工艺概览 / 设备运行 / 历史趋势 / 告警与记录 / AI分析**；需要时再添加“用水/能效”专属Tab。
4. 工艺概览：主图为工艺或区域示意；右侧为关键设备与告警列表；鼠标点击节点打开设备详情抽屉。
5. 设备运行：可筛选设备卡、状态和关键参数；允许进入设备详情和工单。
6. 历史趋势：最多2–3组主趋势，允许多曲线对比、缩放及异常标记；无数据则提供明确说明。
7. 告警与记录：与运维中心共用同一事件数据源；不重复造独立告警表。
8. AI分析：显示当前系统上下文，预置2个专业问题，允许调用受限工具；显示来源和计算依据。

| HOME-01 | 顶部 | 总用水量、再生水利用指标、六系统运行状态、待处置事件 | 每张卡可下钻，口径与其他页面一致 |

| 内部Tab | 布局与功能点 | 可操作演示 |

### 5.3 中压供水 PROC-MP（P0，核心智能演示系统）

**专属关键指标：** 供水压力、瞬时/累计流量、运行泵组、计量电耗；电伴热温度状态纳入工艺监控（若有数据）。

| 内部Tab | 布局与功能点 | 可操作演示 |
| --- | --- | --- |
| 工艺概览 | 泵组→阀门→供水管线示意；右侧显示压力、泵组和电伴热 | 点击泵/阀/伴热进入状态卡 |

**限制：** 同工况才能排名；缺流量/电量时只能显示基础运行指标，不计算真实单位水电耗；电伴热不因缺测点而虚构值。

### 5.4 含矿污水处理 PROC-MINE（P0）

**专属关键指标：** 设计处理能力参考值（约500m³/h）、当前/模拟负荷、处理量、进出水水质（若有）、关联异常。

| 内部Tab | 布局与功能点 | 可操作演示 |
| --- | --- | --- |
| 工艺概览 | 来水→提升→处理→清水→回用的**逻辑**流程，节点类型来自原方案 | 点击处理节点显示状态、参数和关联设备 |
| 设备运行 | 提升泵、净水器、加药、排泥设备台账及状态 | 设备详情/运行历史/维修入口 |
| 历史趋势 | 处理量、处理负荷、出水浊度等可用指标 | 模拟负荷升高，趋势与告警联动 |
| 回用去向 | 处理后合格水、清水池、回用去向的业务归属（待确认项可标注） | 与水资源账本跳转关联 |
| AI分析 | 处理负荷趋势、设备异常与工单建议 | “处理负荷增大，需要重点看什么？” |

**限制：** 水质是否达标仅在有标准、测点及判定条件时计算；不让模型自动调整加药或排泥控制程序。

### 5.5 雨水收集 PROC-RAIN（P0，简化工艺+轻量“四预”）

**业务表达重点：** 港区大面积雨水经现有设施收集、蓄存、沉淀及管网输送。第一期只表现湖/池/区域的水量和运行管理，不绘制地下管网的真实空间与复杂水力路线。

| 内部Tab | 布局与功能点 | 可操作演示 |
| --- | --- | --- |
| 工艺概览 | 业务逻辑示意：收集区域、北/南池体、生态蓄水、人工湖、处理去向；不表达未经确认的管路 | 点击“北区/南区/湖区”查看对象卡 |
| 储水与水位 | 当前/模拟储水、可用库容、液位趋势、分区筛选 | 切换区域时图表同步变化 |
| 雨次分析 | 近3次预置降雨的分区收水量及趋势 | 选雨次→比较→生成AI图表 |
| 四预入口 | “未来24小时假设降雨”轻量情景表单 | 改雨量/初始水位/处理能力→曲线变化 |
| 告警与记录 | 液位风险、泵阀异常、收集事件历史 | 事件详情/建议查看 |

**容量处理：** 9,900m³初雨能力与31,500m³清洁池、19,589m³生态池、约9,649.9m³人工湖等资料口径保留独立来源及待核标签。不得将不同口径简单相加称作真实总容量，不使用“几百亩”作为未经证实的精确参数。

### 5.6 水池供水 PROC-POOL（P0，强调供水保障，不复制中压泵组）

**专属指标：** 可用水量、储水水位、补水来源、供水去向、预计保障时长（仅在假设满足时）。

| 内部Tab | 布局与功能点 | 可操作演示 |
| --- | --- | --- |
| 工艺概览 | 水池/清水池/除尘水池的示意节点与供水方向（待确认边） | 点击池体查看容量、来源与去向 |
| 储水监测 | 按池体查看液位、可用库容及历史记录 | 切池、时间筛选、异常跳转 |
| 供需分析 | 需求假设、用水计划、储量变化及缺口提示 | 调整需求→预计保障时间变化 |
| 水源关联 | 雨水/回用水/自来水的类别及可达约束说明 | 一键转“水资源管理/三水源分析” |
| AI分析 | “现有储量在当前需求下能保障多久？” | 显示计算假设与限制 |

**职责界限：** 泵组压力/效率属于中压供水；跨系统水源方案属于水资源管理/智能决策；消防储备不得被普通经济配置占用。

### 5.7 生活污水处理 PROC-LIFE（P0，保守示意）

**专属指标：** 处理单元状态、处理量、关键水质（如已有DO、ORP等）、告警和巡检任务。

| 内部Tab | 布局与功能点 | 可操作演示 |
| --- | --- | --- |
| 工艺概览 | 进水→处理单元→出水的简化流程，标识“结构示意/待确认” | 点击处理单元，进入设备状态 |
| 设备与运行 | 工艺设备状态及基础运行记录 | 按运行状态筛选、进入详情 |
| 监测趋势 | 可用水质或运行参数与告警时点 | 在模拟异常场景中观察趋势 |
| 运维记录 | 巡检、维护、异常事件 | 查看工单并录入处理反馈 |
| AI分析 | 稳定性分析、基于知识库的排查清单 | 从异常生成待确认巡检任务 |

**限制：** 禁止凭空添加MBR、曝气池型号、药剂种类或工艺能力；没有数据的指标显示未接入，不填写占位的虚假实时数值。

### 5.8 工艺页交叉联动的统一规则

- 任何工艺页可点击设备→进入统一设备详情，不再为每套系统开发一套不同的设备弹窗。
- 工艺告警和运维中心使用同一事件ID，工单通过关联事件ID追溯。
- 时间范围、设备筛选、数据模式、用户权限应跨下钻页保持一致。
- “一键AI分析”必须带入当前工艺、对象、时间和已选指标，不得让用户重新输入上下文。
- 每个工艺页默认提供2条可执行预置问题，问题和结果与该工艺相关，不泛泛回答。

## 6. 横向业务功能需求与布局

### 6.1 水资源管理 WATER（P0基础、P1辅助匹配）

| 页面 | 布局 | 必须展示 | 交互要求 |
| --- | --- | --- | --- |
| 水资源总览 | 4个概览指标 + 中央水流逻辑 + 下方来源用途统计 | 水源、回用水、库存、终端用水 | 点击来源/去向可下钻，支持日期 |
| 雨次分析 | 顶部雨次/南北区域筛选 + 主图 + 对比表 | 历次降雨收水量及容量变化 | 时间/区域切换，AI图表生成入口 |
| 水量账本 | 来源、处理状态、储存节点、终端消耗分层表 | 逐项进出量及平衡差 | 按类别筛选，查看口径和未计量项 |
| 三水源分析（P1） | 左条件区 + 中方案区 + 右解释区 | 安全、经济、节水模式的方案比较 | 修改可用水量/需求→结果变化 |

**水量口径：** 不把“收集雨水”“处理后的同一份回用水”“终端消耗”作为三个互相独立的供水量相加。水量平衡定义为期末储量=期初储量+流入−流出−损失±统计误差。缺少仪表时展示估算或不可计算状态。三水源方案基于现有或假设的水质合规、管网可达、可用量与保障边界；不生成真实现场切换命令。

### 6.2 设备健康与能效 DEC-HEALTH（P0）

**布局：** 顶部设备类型/系统/时间筛选；左侧同类设备排行（30%），中间趋势与比较图（45%），右侧评分依据与AI建议（25%）；小屏改纵向。

| ID | 功能点 | 规则及验收 |
| --- | --- | --- |
| HEALTH-01 | 按系统/设备类型/时间选择可比较设备 | 不同设备类别不可直接统一效能排行 |
| HEALTH-02 | 健康基础评分与数据完整性 | 明示指标、权重、缺项、评价等级；无数据可不评分 |
| HEALTH-03 | 同类泵能效对标 | 同一计量边界下kWh/m³；可比工况约束明确 |
| HEALTH-04 | 历史变化与异常标记 | 单位时间段变化与事件对应，图表可跳到事件 |
| HEALTH-05 | AI建议解释 | 展示依据、可能原因和建议检查项目 |
| HEALTH-06 | 生成工单草稿 | 人工确认后写入工单数据库，设备详情可见 |

不能用额定功率直接代替实测电耗，也不承诺剩余寿命预测。健康评分只服务于“风险排序与检查建议”，不是设备安全鉴定。

### 6.3 微观“四预” DEC-FOUR（P0一个基础情景）

**布局：** 左侧情景参数表单（约300px）+ 中部预测曲线/水位变化（自适应）+ 右侧风险提示/方案对比（约320px）；顶部有场景预设及重置按钮。

| 四预环节 | 首期必须具备的产品行为 | 数据说明 |
| --- | --- | --- |
| 预报 | 根据假设降雨、初始储量和处理能力计算未来库容序列 | “模型估算/演示情景” |
| 预警 | 预计达到阈值时标示风险时段和受影响区域 | 规则产生，不是现场正式预警 |
| 预演 | 对比“保持现状/提前处理”等策略的预测曲线 | 参数变化须重新计算 |
| 预案 | 输出可编辑检查清单/调度建议草稿 | 需人工确认，不调用真实PLC |

**最小公式：** `V(t+Δt)=V(t)+(Qin−Qout)*Δt`。输入雨量可以按“降雨深度×有效汇水面积×径流系数”做演示估算；所有假设可查看、可修改、可恢复默认。总容量只能使用经过来源归类的模拟配置或明确的设计参考值，不自动合并有口径冲突的池体。复杂多池水力动力模拟不做。

### 6.4 告警事件 OPS-ALARM（P0）

| 区域 | 内容 | 操作 |
| --- | --- | --- |
| 顶部筛选 | 系统、等级、状态、时间、关键词 | 查询、重置、导出（P1） |
| 中间列表 | 事件编号、设备、级别、首次/最近发生、状态 | 点击详情；有权限者确认/处理 |
| 右侧事件抽屉 | 告警时间线、关联趋势、相关设备、AI原因提示 | 查看证据、生成工单草稿 |
| 批量操作 | 多选同类事件 | 仅授权角色进行批量确认，操作须审计 |

事件生命周期：新发生→已确认→处理中→已恢复/已关闭；异常恢复与业务关闭是两个不同概念。相同故障的重复告警在演示中可合并展示，但保留原始记录。

### 6.5 工单任务 OPS-WO（P0）

| 功能 | 用户操作 | 结果 |
| --- | --- | --- |
| 新建工单 | 手工创建/告警转单/AI草稿 | 草稿可修改设备、责任人、优先级 |
| 提交 | 检查必填字段后提交 | 产生工单ID，待处理队列立即出现 |
| 派发 | 有权限的人选择人员/班组 | 受派人员的待办更新 |
| 办理 | 填写措施、图片/附件模拟、处理结果 | 进入待验收或待关闭状态 |
| 关闭 | 授权人员审核并关闭 | 事件关联、操作日志、建议反馈同步更新 |
| 搜索追踪 | 查询编号/设备/状态 | 详情包含完整状态流转时间线 |

DEMO不得把“AI生成工单草稿”说成“已实际维修”。至少能完成草稿→提交→办理→关闭的可复位模拟闭环。

### 6.6 数据与报表 DATA（P0/P1）

常用报表提供用水、设备、告警、工单四类模板；AI工作台允许自然语言生成临时分析；“我的看板”保存个人布局；“历史分析”保留AI请求、数据时间范围、schema版本与结果快照。报表导出可优先Excel/CSV/打印，复杂Word/PDF排版作为P1，避免拖累P0。

## 7. 用户自定义页面、功能、菜单与配置体系（重点）

### 7.1 “自定义”必须区分五层

| 层级 | 使用人 | 可配置内容 | 不可触碰内容 | 首期 |
| --- | --- | --- | --- | --- |
| A 个人展示配置 | 所有授权用户 | 首页非关键卡片顺序、图表、主题密度、默认筛选、收藏 | 原始数据、权限、关键安全告警 | P0 |
| B 个人AI工作台 | 所有授权用户 | 自然语言生成图表、布局、筛选、组件替换、保存版本 | 任意JS执行、越权数据、控制指令 | P0 |
| C 岗位模板 | 业务负责人/管理员 | 按角色分配默认首页和专题模板 | 只能在角色可读数据范围内发布 | P1 |
| D 后台功能配置 | 系统管理员 | 菜单显示、模块开关、表格字段、表单模板、规则草案 | 不能绕过RBAC/安全联锁 | P0基础/P1完善 |
| E 开发组件扩展 | 研发人员 | 经过代码评审的新组件、数据工具、AI动作 | 不允许运行时无审核生成源码上线 | P1/P2 |

### 7.2 个人工作台配置（P0）

用户可以在“我的工作台”执行“新增卡片、删除非必备卡片、移动/缩放卡片、更换图表、添加筛选器、设置默认时间、保存布局、另存为模板、恢复默认”。页面编辑采用显式编辑模式；拖拽时显示网格和占位，不在普通查看模式下误拖动；关键告警与安全状态组件设置为锁定。

个人配置模型最少包含：`dashboardId`、`ownerId`、`scope=personal`、`title`、`layoutVersion`、`widgets[]`、`dataBindings[]`、`filters[]`、`createdAt`、`updatedAt`；支持版本历史和一键恢复。个人看板可按权限分享为只读链接/共享模板，默认不公开。

### 7.3 自定义表格及表单（P1）

- 表格：列显隐、列顺序、固定列、宽度、排序、筛选条件、导出列、保存个人表格视图。
- 表单：管理员可配置非关键业务的必填、可见、展示顺序和帮助文案；字段类型必须来自允许清单；更改须版本化。
- 新增数据库字段/物理表不能由普通用户的“帮我加一列”隐式完成；应优先生成**虚拟分析列、计算字段或自定义视图**。
- 用户请求添加计算指标时，需要选择已有字段并校验表达式的单位、空值、时间聚合和数据权限；不能任意执行SQL或脚本。

### 7.4 系统菜单/功能开关（P0基础）

管理员可对已注册模块进行启用/禁用、指定允许角色、配置排序与导航名称、指定页面模板；菜单被禁用后路由和API操作同样受控。功能注册表最少包含：`featureCode`、`name`、`route`、`componentKey`、`requiredPermission`、`enabled`、`minDataRequirements`、`configSchemaVersion`。

**注意：** “自定义页面”是用户体验能力，“自定义业务规则”是业务配置能力，“修改源代码”是研发发布行为，三者必须分离。AI可以建议变更，但不能自行跨越界限。

### 7.5 岗位模板发布流程（P1）

管理员新建或复制模板→选择适用角色及数据范围→组件和指标配置→预览权限效果→提交审批/确认→发布→指定默认模板→记录版本；普通用户可以在岗位模板基础上做个人化调整，但不改变公共模板本身。

### 7.6 AI自然语言改页面的边界（P0）

支持的指令示例：

1. “把右边的水量图改成折线图。”→修改UI schema的图表类型。
2. “增加最近30天中压泵组异常次数表。”→校验数据权限和指标后新增受控表格组件。
3. “把这个图放到我的首页第二行。”→生成带预览的布局变更，用户确认后保存。
4. “隐藏不需要的设备分类卡片。”→仅修改本人的可隐藏组件，不删除后台数据。
5. “为值班员新增一套日报模板。”→生成模板**草稿**，需有配置权限的人发布。
6. “新增一个平均电耗字段。”→生成虚拟指标/计算列的草稿并校验单位，不直接ALTER数据库。

AI执行流程：解析需求→检查当前页面与权限→查询注册指标与组件→生成修改差异→后端校验→展示预览→用户确认→保存新版本→反馈成功。失败时保留原版，并解释原因。

### 7.7 配置后台页的布局

推荐左列为配置对象树（系统/页面/模板），中部为属性与规则编辑区，右侧为实时预览与权限检查；底部抽屉展示变更版本和审计。切勿让配置项全部堆在一个超长表单内；“个人配置”和“管理员配置”入口分开。

## 8. AI生成式UI与Agent工作流（核心技术亮点）

### 8.1 AI分析工作台 DATA-AI（P0）

**布局：** 顶部分析标题/数据时间/保存按钮；中央70%左右为可交互画布（空状态显示建议问题和模板）；右侧30%左右为可折叠的AI对话、工具执行与来源抽屉。初次进入不强制空白，展示三条可点击示例：“南北雨次分析”“泵组健康对比”“昨日异常总结”。

| ID | 用户指令 | 必须看到的结果 |
| --- | --- | --- |
| GEN-01 | “比较最近三次降雨南北集水池收水量，生成柱状图。” | 真实创建组件并绑定固定模拟数据集 |
| GEN-02 | “加上用电量折线。” | 有可用能耗指标才生成组合图；缺数据解释并给替代建议 |
| GEN-03 | “按收水量降序，加平均值。” | 更新表格排序及统计行，保留先前内容 |
| GEN-04 | “把图移到左上并加一个总量卡。” | 可预览布局差异、确认后更新画布 |
| GEN-05 | “保存为雨次分析看板。” | 新建dashboard记录、版本号，重开仍在 |
| GEN-06 | “生成中压供水同类泵健康能效对比。” | 更换分析上下文，输出带依据的结果 |
| GEN-07 | “撤销刚才的修改。” | 恢复上一schema版本 |
| GEN-08 | 输入不存在的指标/越权对象 | 不执行；解释原因、列出可用指标 |

### 8.2 受控生成架构

AI输出**声明式页面Schema**，只能使用注册的组件：`KpiCard`、`LineChart`、`BarChart`、`DualAxisChart`、`DataTable`、`FilterPanel`、`AlertList`、`TextSummary`、`AssetCard`、`ScenarioCompare`等。不得接受任意HTML/JS、字符串拼接的SQL、未审核URL脚本或动态Vue源码。

```json
{
  "schemaVersion": "1.0",
  "title": "南北集水池雨次对比",
  "dataSetRef": "rainfall.events.latest3",
  "filters": {"area": ["north", "south"]},
  "widgets": [
    {"id": "rain-compare", "type": "BarChart", "metricRefs": ["rainwater.collected_m3"], "groupBy": ["event", "area"], "layout": {"x": 0, "y": 0, "w": 8, "h": 5}}
  ]
}
```

数据查询先由后端生成白名单查询计划：数据集→授权范围→指标口径→查询预算→聚合→结果校验。AI仅获得必要字段，不直接获取数据库写权限。保存时持久化schema与数据绑定，支持渲染器版本升级迁移。可参考A2UI开放协议，但当前原生Vue渲染应采用自有可信组件适配层。

### 8.3 全局AI助手（P0）

从任一页打开AI抽屉时自动传入：当前系统`subsystemId`、设备`assetId`（如有）、时间范围、选中图表和用户权限。对话回答包括简要结论、可视化结果/链接、引用指标及下一步动作；允许“展开分析工作台”。在浏览器刷新后能恢复最近已保存任务。

### 8.4 Agent协同（P0最小闭环）

主Agent负责意图识别和工具编排；工具包括：设备查询、时序统计、健康评分、能效对比、知识检索、生成图表、工单草拟、审批提交、报表导出。初期可使用**一个主Agent+受控工具**，不用拆成很多独立模型。

可视化流程：用户输入→权限判定→数据查询→规则/模型计算→解释建议→创建工单草稿→人工确认→状态更新→执行日志。每步展示“已完成/失败/待用户确认”，不能出现模型实际上没调用工具却宣称已创建工单的情况。

### 8.5 AI持续成长（P1）

- 保存经过审核的设备知识、历史处置案例和管理规则，并显示引用来源。
- 将用户选择保存的看板与常用分析模板作为个人偏好，不自动篡改公共工作台。
- 记录AI建议、人工反馈及处理结果，用于离线评估与下一版本优化。
- 模型、提示模板和工具定义必须有版本、自动化测试与回滚；不允许自我改写程序、自我部署和自我审批。

### 8.6 AI故障与降级

AI模型不可用时，固定工艺、设备、告警、工单和已有看板照常可用；可使用明确标注为**规则引擎/预置模板**的离线演示流程，不能把硬编码模板假称实时生成。错误结果不覆盖已保存页面，用户可撤销或回退。

### 8.7 语音与蓝牙扩展

本期P1提供PC/移动端按键语音输入、识别结果预览、手动确认发送；ESP32-S3仅作为可选音频采集终端，中文自由语音转写主要由服务端ASR完成。BLE无现有广播信号则需要新增设备；第一期不把免扫码后台自动打卡作为纯软件承诺，仅预留移动巡检的设备发现适配接口。

## 9. 数据模型、模拟场景与指标规则

### 9.1 统一数据模型（建议最小实体）

| 实体 | 核心字段（示例） | 使用场景 |
| --- | --- | --- |
| User / Role / Permission | id、roles、orgScope、subsystemScope、actionCode | 角色菜单与动作鉴权 |
| Subsystem | id、name、type、status、dataMode | 六工艺入口、系统筛选 |
| Asset | id、subsystemId、type、name、ratedParams、status | 设备详情、运维 |
| MetricDefinition | code、unit、formula、aggregation、sourceType、requiredInputs | AI查询、统计口径 |
| Point / Sample | pointId、assetId、metricCode、ts、value、quality | 设备和趋势数据 |
| WaterNode / WaterEdge | id、type、capacity、area、from/to、verified | 水量账本与逻辑水网 |
| RainEvent | id、startAt、endAt、area、depthMm、mode | 雨次对比/情景预演 |
| AlarmEvent | id、assetId、level、status、timeline、evidence | 告警关联、AI诊断 |
| WorkOrder | id、assetId、sourceEventId、assignee、status、history | 工作流及审计 |
| Dashboard / Widget | id、owner、scope、schema、version、layout | 个人/岗位看板 |
| AiTask / ToolTrace | prompt、modelVersion、toolName、status、resultRef、approval | Agent过程、审计 |
| Scenario / Assumption | scenarioId、seed、inputs、outputs、mode、resetVersion | DEMO可重复演示 |
| AuditLog | user、action、resource、before/after、timestamp、traceId | 操作可追溯 |

### 9.2 至少四套可重置的演示场景

| 场景ID | 场景主题 | 关联页面 | 必须联动的结果 |
| --- | --- | --- | --- |
| SCN-BASE | 正常运行基线 | 首页、六工艺、设备 | 无重大异常，默认数据自洽 |
| SCN-RAIN | 连续降雨与储量变化 | 雨水、水量、四预、AI分析 | 雨次、库容、预警、模型曲线同源 |
| SCN-PUMP | 中压泵低效/故障风险 | 中压、健康能效、告警、工单 | 趋势异常→建议→工单状态关联 |
| SCN-MINE | 含矿污水负荷/水质异常 | 含矿、事件、AI、运维 | 负荷变化、报警与任务形成一致结果 |

场景数据固定seed，预置时间不依赖当前真实日期（例如使用“演示第1天”等相对标签）；一键切换与重置应更新所有页面，不允许首页仍显示上一场景数据。场景切换前提醒将覆盖当前演示业务数据，并支持默认快照恢复。

### 9.3 一致性约束

- 每个模拟测点只有一份权威数据，首页汇总、设备详情和AI分析基于同一API与同一指标定义。
- `design_reference`、`simulated`、`calculated`、`model_estimate`、`measured`分类字段必须贯穿API返回，不能只在UI上贴一个“演示”字样。
- 再生水与雨水的来源、处理状态、终端用水分别核算；不重复统计流转量。
- 能效采用`电耗(kWh)/有效水量(m³)`；跨设备比较需明确设备类型和工况；分母为0或无计量数据时返回不可计算。
- 设备健康为可解释的规则分数，不得宣传为可靠的剩余寿命预测；缺项时降低可信度或不输出评分。
- 模拟AI建议的收益必须来自当前场景模型或明确的“假设值”，不把静态“预计节能5%”写死到页面文案。
- 所有用户修改行为必须更新持久化状态；数据模式切换不修改原设计参考参数。

### 9.4 数据缺口的明确展示

数据缺失要呈现“未接入/未提供/不可计算/待确认”，并能通过“为什么不能分析？”查看缺少的输入，不用0替代未知，也不让AI编造数字。对用户提供替代方案，例如“缺少流量计，改为比较运行电耗与时长”。

## 10. 推荐技术路线：AI辅助开发友好、先进且可落地

### 10.1 核心技术决策

**推荐：TypeScript作为主语言贯穿前端、业务API、Schema、权限和Agent工具；Python只用于需要专门数学优化、预测或模型服务的模块。** 原因是同一类型体系有利于AI编码助手跨前后端修改、降低接口契约漂移；数据模型/复杂算法可用Python模块独立演进。对本期DEMO，不必一开始拆微服务。

| 层次 | 建议技术 | 选择理由与约束 |
| --- | --- | --- |
| 前端 | Vue 3（Composition API）+ TypeScript 6 | 延续既有项目技术积累，强类型、组件复用、AI辅助编码友好 |
| 工程构建 | Vite 8稳定维护分支 + pnpm Workspace | 开发/构建快，多包共享合同；锁定依赖与版本 |
| 路由 | Vue Router | 二级子菜单、权限路由与页面上下文 |
| 客户端状态 | Pinia | 登录、当前工艺、页面布局等客户端状态 |
| 服务端数据 | TanStack Query for Vue | 请求缓存、刷新、分页、错误和状态同步 |
| UI组件 | Naive UI + 自有业务组件 | 统一表单、抽屉、表格与工业业务风格；检查Vite/TS兼容性 |
| 样式 | UnoCSS + CSS变量Design Tokens | 浅色科技风统一约束、响应式和主题切换 |
| 图表 | Apache ECharts 6.x | 多类型图表，适合Schema组件渲染 |
| 业务API | NestJS 11模块化单体（优先Fastify适配，须做兼容性验证） | 清晰模块/权限/DTO，后续便于扩展；DEMO不必微服务 |
| 数据库 | PostgreSQL（本地Docker Compose） | 用户、配置、工单、时序模拟记录与审计一致持久化 |
| 共享接口 | OpenAPI + TypeScript类型生成 + Zod运行时校验 | AI生成代码不靠猜接口，数据查询和UI Schema可验证 |
| AI执行 | TypeScript工具调用编排 + 可选LangGraph工作流 | 首期单主Agent；复杂持续任务再引入状态化编排 |
| AI模型 | 标准模型适配接口（本地优先/可切换） | 避免与特定模型、GPU型号、云服务强绑定 |
| 计算模型 | TypeScript基础规则 + Python FastAPI按需扩展 | 简单水量/健康/能效在TS中完成；后续复杂优化独立 |
| 测试 | Vitest + Playwright + API契约测试 | AI生成代码必须经自动化验证 |
| 启动 | pnpm脚本 + Docker Compose（仅数据库，可离线演示） | Mac本地可一键启动；不依赖公网持续连接 |

**版本策略：** 以2026年11月已发布的稳定版为参考，选用经过依赖兼容测试的补丁版本并提交`pnpm-lock.yaml`。Node.js 26已经进入LTS，可优先验证；若部分依赖不兼容，采用Node.js 24 LTS而不是强行升级。TypeScript 6存在行为与默认值调整，需要明确`tsconfig`并测试，不盲目跟随试验版本。

### 10.2 为什么不选全新陌生框架重写

用户已有Vue 3和TypeScript开发能力以及历史UI组件基础；为追逐React、Next或某种新“AI框架”整体迁移将增加模型生成质量之外的开发和维护风险。**“最适配AI开发”首先依赖明确的数据合同、稳定组件、可测试任务和可复现工程，而不是换掉熟悉的技术栈。** 当前官方A2UI 1.0提供React/Angular/Lit等Web渲染器，但没有官方Vue原生渲染器；DEMO先以自有Vue Schema驱动界面，未来预留A2UI适配器。

### 10.4 开发规则（直接交给AI编程工具）

1. 所有新增页面先登记`pageId/route/permissionCode/dataDependencies`，不直接在导航组件里手写散落菜单。
2. 所有API先定义DTO/OpenAPI与错误码，再写后端实现和前端消费；在CI中验证契约一致。
3. 所有业务指标只定义一份计算规则和计量单位，禁止同一个指标在前后端重复实现不同公式。
4. AI生成式UI的组件必须从注册表白名单解析，生成schema先校验后渲染；组件必须有空态/加载/错误/无权限态。
5. 所有模拟数据从`fixtures`读取，运行时统一经过场景API；禁在Vue组件中硬编码今日用水、健康评分或节能收益。
6. 事件、工单、个人看板写入数据库并审计；演示切换角色时验证菜单、按钮与API三端一致。
7. 严格TypeScript模式、禁止`any`滥用；业务常量及权限码采用共享类型；不接受静默吞错的`catch{}`。
8. 每个关键模块至少配单元测试和一条端到端操作测试；AI修改代码后先跑`typecheck/lint/test/build`再合入。
9. 默认保留浅蓝/白磨砂UI设计令牌，不在各页面新增不一致的主题颜色和硬编码间距。
10. 逐模块小步开发、可回滚；先做稳定DEMO再增加多模型和自动化能力；本地源码交付不含`dist`、不包含秘钥和真实数据。

### 10.6 生成式UI接口和服务划分

- `POST /api/ai/parse-intent`：分析自然语言的页面/查询/业务动作意图。
- `POST /api/metrics/query`：校验用户授权、指标和聚合预算，返回结构化数据。
- `POST /api/ai/ui/compose`：生成或修改页面Schema及差异，不返回可执行源码。
- `POST /api/dashboards`：用户确认后持久化看板和版本。
- `GET /api/ai/tasks/:id`：查看工具调用过程和最终结果。
- 任何具有写入效果的业务工具通过同一后端权限机制，不因来自Agent而放宽。

## 15. V1.2 范围收敛与需求完成定义（新增）

### 15.1 四级交付状态（区别于业务优先级）

为避免“P0都要做”造成DEMO范围失控，每条需求同时标记**业务优先级**与**实现深度**：

| 实现深度 | 定义 | 允许的演示方式 | 验收标准 |
| --- | --- | --- | --- |
| L0 导航可达 | 正确菜单、路由、角色访问和状态说明 | 可使用工艺示意及设计参数 | 可进入、可返回、不空白、不虚构现场数据 |
| L1 数据可查 | 统一模拟数据驱动的列表、指标、趋势、详情 | SIM数据，来源标识 | 同一对象跨页面值一致，筛选有效 |
| L2 业务闭环 | 创建、修改、确认、提交、反馈可持久化 | 模拟业务动作，非现场控制 | 状态变化、ID关联、审计、刷新后不丢失 |
| L3 智能交互 | AI/规则引擎产生受控页面、分析或方案，能解释依据 | 本地模型或明确标识的规则/模板降级 | 输入变化产生可复核的差异，错误可恢复 |

**一期首批必须完成的端到端功能**限定为：①六工艺菜单与差异化详情（L1）；②中压泵分析→AI检查建议→工单（L2/L3）；③雨水/池体简单情景模拟（L3，明确估算）；④生成式图表→多轮调整→保存重开（L3）；⑤管理者/值班员/运维三种角色的授权差异（L2）。

其他能力**保留需求、降低首期深度**：公共岗位模板发布、复杂自定义业务规则、三水源多目标求解、移动端深度巡检、ESP32及BLE均不是首批演示的必备验收点。文档其他章节若出现更高的原定优先级，以本节作为V1.2首批交付口径。

### 15.2 三项核心成功标准（按业主感知排序）

1. **简单**：管理者在首页识别整体状态、进入任一工艺不超过两次主要点击；常用报表无需进入配置后台。
2. **智能**：输入业务语言后真实产生图表或任务，不以预置图片替代；至少一个智能分析可展示输入、计算、依据和限制。
3. **可信**：模拟/设计/计算/AI建议严格区分；缺少仪表时明确“未提供/不可计算”；任何AI动作不得越权。

### 15.3 需求条目定义模板（所有新增需求遵循）

每个需求记录：`需求ID`、`页面/角色`、`业务目的`、`输入和数据条件`、`触发动作`、`计算/状态规则`、`输出`、`权限`、`优先级与深度`、`异常及空态`、`验收用例`。禁止只写“支持智能分析”“支持配置”却不给出交互与可复核结果。

## 16. 导航、角色及业务操作的精确定义（新增）

### 16.1 导航信息架构与页面归属

左侧保留七个一级菜单：综合总览、工艺监控、水资源管理、智能决策、告警与运维、数据与报表、系统管理。**工艺监控只展开六个系统子菜单**；设备详情、趋势、告警及AI分析在当前工艺内部通过Tab或抽屉进入，不再增加第三层左导航。

工艺导航固定顺序：`射雾器除尘` → `中压供水` → `含矿污水处理` → `雨水收集` → `水池供水` → `生活污水处理`。进入系统时在导航中高亮，保留最近的内部Tab与筛选；权限变化、注销、切换模拟角色时清理不可访问的页面缓存。

| 使用场景 | 导航交互 | 结果 |
| --- | --- | --- |
| 点击“工艺监控” | 展开六个子菜单；其他主菜单的展开组收起 | 不导航到空白占位页 |
| 点击某个子菜单 | 跳转工艺路由并显示专属概览 | 高亮当前系统；保留已授权的时间筛选 |
| 从首页热点进入工艺 | 进入相同路由并展开相应子菜单 | 不复制另外一套工艺页面 |
| 从告警进入设备 | 跳转工艺/设备抽屉，带`assetId`与`eventId` | 显示相同事件和趋势时间窗 |
| 角色无工艺权限 | 菜单不可见；直达URL返回403业务页 | 后端数据访问同样拒绝 |
| 系统模块关闭 | 菜单、路由、API动作同步受控 | 已保存的数据保留，页面解释功能已停用 |

### 16.2 角色职责不等于直接授予操作权限

以“角色默认权限 + 组织/工艺数据范围 + 具体动作授权”为准。角色仅是DEMO默认模板；正式部署可按业主岗位配置。管理员拥有配置权限但**不自动**拥有生产操作或业务审批权。

| 角色 | 登录默认页 | 工艺/数据 | 可执行动作 | 不允许动作 |
| --- | --- | --- | --- | --- |
| 管理者 | 综合总览 | 已授权六系统指标与报表 | 生成个人分析、查看建议、按授权审批模板/方案 | 默认不能确认告警、代办维修、管理账号 |
| 值班员 | 今日关注/分管工艺 | 分管系统实时与历史 | 确认告警、发起工单、记录异常、保存个人看板 | 发布系统级规则、调整权限、越权查看其他区域 |
| 运维人员 | 我的工单/设备 | 负责设备及相关事件 | 接单、处理、上传记录、反馈AI建议 | 变更其他班组任务、直接修改设备基准指标 |
| 水资源人员 | 水资源管理 | 雨水、用水、处理、回用授权数据 | 生成分析与情景、草拟调度方案、导出报告 | 直接执行水源切换或泵阀控制 |
| 平台管理员 | 管理后台 | 管理所需配置元数据 | 管用户角色、菜单开关、岗位模板、指标注册、演示场景 | 不能仅凭管理员身份执行生产控制 |
| 只读访客 | 审核过的看板 | 授权脱敏数据 | 浏览、查看报告 | 新建工单、修改看板、导出受限数据 |
| 演示主持人 | 演示控制台 | 固定模拟场景 | 选择种子场景、复位、展示角色对比 | 切换到真实用户权限或写入生产数据 |

### 16.3 一条跨角色业务链（P0）

## 20. DEMO数据场景、业务状态与跨页一致性（新增）

### 20.1 场景数据库与标识要求

四套场景继续采用`SCN-BASE / SCN-RAIN / SCN-PUMP / SCN-MINE`，由统一种子数据/固定随机种子初始化。首页、工艺、趋势、AI、告警和工单从同一API读取，不得在Vue页面或AI提示词里硬编码互相矛盾的数据。

所有返回数据包含`dataMode`（SIM/REF/CALC/AI/MEASURED）、`scenarioId`、`asOf`、`metricCode`、`unit`、`quality`；涉及计算的数据另带`formulaVersion`、`assumptions`与`inputRefs`。

### 20.2 泵组演示的最小可核对数据关系

用于内部测试的纯模拟例子：泵A在一个可比时段内供水400m³、耗电100kWh，则单位水电耗0.25kWh/m³；泵B供水420m³、耗电84kWh，则为0.20kWh/m³。**仅在相同设备类型、计量边界和可比工况模拟前提下**可排序；健康度由另一组故障/运行规则计算，不能以单位水电耗代替健康评分。该数据不来自唐港现场，不应在对外汇报时被当作实测成果。

### 20.3 雨水模型与水量守恒

- 采用简化离散水量平衡：`V_next = clamp(V_current + Qin*Δt - Qout*Δt, 0, Capacity)`；超过Capacity的部分记为`unserved_or_overflow`，不允许凭空消失。
- 雨量入流估算仅对已定义的汇水面积、径流系数和转化效率成立；实际湖区面积、池容口径未知时使用**明确标注的演示假设**。
- 每次调整降雨、初始储水或处理负荷，必须更新曲线、峰值、风险提示和方案对比，不允许只改展示标签。
- P0只建单汇总储水单元或按已确认逻辑聚合的简化多单元，不模拟真实地下管网水动力；复杂初雨/清洁雨水分流在说明层保留，不假称精确预测。

### 20.4 告警与工单状态定义

| 对象 | 状态 | 触发/限制 |
| --- | --- | --- |
| 告警事件 | `new / acknowledged / handling / recovered / closed` | 恢复条件与人工关闭分开；关闭需记录人/时间/处理说明 |
| 工单 | `draft / submitted / assigned / in_progress / pending_review / closed / cancelled` | 只允许合法顺序迁移；取消与关闭不等价 |
| AI任务 | `queued / running / awaiting_approval / completed / failed / cancelled` | 每步工具调用可追踪；模型失败不能伪装为完成 |
| 页面配置 | `draft / previewed / published / archived` | 个人看板可直接保存，公共岗位模板另需发布权限 |
| 模拟场景 | `inactive / active / reset_pending` | 切场景确认范围；不影响真实用户历史记录 |

状态流转由后端服务控制，前端仅提交事件和参数，不直接把对象状态改成任意字符串。

### 20.5 演示复位的副作用控制

主持人点击“恢复初始场景”时，弹窗显示影响范围：模拟采样、告警事件、工单及AI任务记录；允许选择保留个人看板，默认保留，以便演示“保存并重开”。复位操作产生审计日志；真实项目资料、业务规则定义和原始设计参数不可被重置脚本删除。

关键角色权限、API响应与状态迁移必须使用单元/集成测试；核心路线使用Playwright端到端测试；文字输出质量与AI工具选择需使用固定中文业务测试集回归。演示前跑一次**全流程重置→完整演示→刷新→重开→降级测试**，不能仅通过截图判断完成。

## 22. AI辅助研发的交付规范（新增）

### 22.1 开发任务拆分：一张任务卡只解决一个可验收业务结果

| 任务组 | 主要输出 | 合并前检查 |
| --- | --- | --- |
| T01 基础骨架 | 路由、菜单、RBAC、Design Tokens、数据库种子 | 六子菜单可达，角色访问受控 |
| T02 统一数据 | Asset/Metric/Alarm/WorkOrder/Scenario等契约与API | 四场景数据一致，公式单测通过 |
| T03 六工艺 | 六个专属配置+统一详情抽屉 | 六系统内容真实不同，数据缺项显示正确 |
| T04 运维闭环 | 告警→建议→工单→审核与反馈 | 状态、ID、审计可持续 |
| T05 决策模拟 | 健康能效、雨水库容公式与方案比较 | 更改参数使输出随之变化 |
| T06 生成式UI | 组件注册表、Schema、AI会话、保存与撤销 | 多轮改图真实渲染；安全校验有效 |
| T07 个性化 | 个人看板、筛选视图、角色默认模板 | 用户之间配置隔离 |
| T08 演示验收 | 复位脚本、完整演示脚本、E2E回归 | 故障/降级路径可重复执行 |

### 22.2 AI编码工具统一工作约束

1. 开始改动前必须读取当前版本PRD、`packages/contracts`、当前ADR及测试；禁止只凭截图和一句需求重构整个系统。
2. 每个任务先提交**文件改动计划与契约变化**，再修改代码；避免同时重构业务和设计风格。
3. 先实现后端行为和模拟数据，再接页面；任何关键交互不能以`setTimeout`模拟“操作成功”而缺少真实状态。
4. 所有权限在后端判定；UI是否显示由同一权限码推导；Agent不能调用更高权限工具。
5. 新功能必须加至少一条成功测试和一条失败/越权测试；全部测试在Mac本地可运行。
6. 保持既有Vue3/TS/Pinia/Naive UI/UnoCSS/ECharts架构；除非有ADR批准，不新增多个状态库、图表库或AI编排框架。
7. 所有秘密写`.env.example`示例变量，真实Key不入库、不入ZIP；源码交付不含`dist`与`node_modules`。
8. 生成式UI结果以schema和数据引用持久化，不存储未审核的运行时代码；AI模型输出失败时不覆盖用户旧看板。

### 22.3 推荐的技术阶段策略

核心工程继续保持**Vue3 + TypeScript + Vite + Pinia + Naive UI + UnoCSS + ECharts**；后端推荐**NestJS + PostgreSQL**，用OpenAPI/Zod共享契约、Playwright做端到端验证。复杂预测与求解器成熟后再独立引入Python服务。框架版本以兼容性测试通过并锁定的稳定版本为准，不把“最新”本身作为验收指标。系统可接本地模型或模型网关，但离线可用性需分别测试业务核心和AI功能。
